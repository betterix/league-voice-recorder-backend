🎧 League Voice Recorder Backend

Ultra-fast, ultra-lean, centralized remote audio storage service for the League Voice Recorder desktop application.

Engineered by Betterix in pure Rust with Axum and Tokio. Built for rock-solid reliability, zero memory leaks, and resilient direct-internet exposure.

Key Highlights • Supported Versions • Quick Start • Access Logging • API Reference • Documentation • Contributing • License

⚡ Key Highlights

  • 🏎️ Ultra-Lean Resource Usage: Operates under 1.35 MiB of resident RAM in production. Bounded 64 KB chunked streaming guarantees zero memory bloat even when transferring hundreds of megabytes.
  • 🔒 Direct-Port Ingress (Native TLS 1.3): Binds directly to port 8443 (TCP) over native HTTPS with OpenSSL AEAD cipher suites (TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256). No Nginx or reverse proxy required.
  • 🐳 Native Multi-Architecture OCI Images: Automatically built and published to GHCR with native hardware compilation for both linux/amd64 and linux/arm64 without emulation slowdowns.
  • 📊 Real-Time Structured Access Logging: Immediate terminal visibility into incoming traffic (client IP, HTTP method, target route, HTTP status, and μs/ms latency) paired with automated healthcheck noise suppression to keep Docker logs clean.
  • 🛡️ Three-Tier Constant-Time Authentication:
  • UPLOAD_KEY: Client recording uploaders (Upload, Download, List, Metadata).
  • PULL_KEY: Analysts, coaches, and review tools (Download, List, Metadata).
  • ADMIN_KEY: Full administrative permissions, bans, and purges.
  • All token comparisons execute in constant time (subtle::ConstantTimeEq) to eliminate timing attacks.
  • 🤖 Automated Bot Shield & Exploit Defense:
  • Zero-Tolerance Scanner Traps: Instant permanent IP ban on probe signatures (/.env, /.git, /actuator, /console, PROPFIND).
  • Heuristic Error Ban: Automatically blacklists scanning hosts exceeding error thresholds (5 invalid requests in 60s).
  • Hybrid VPS / Datacenter Bot Defense: Blocks automated scraping crawlers from cloud datacenters (AWS, DigitalOcean, Hetzner, OVH, Linode) while allowing genuine API clients.
  • Brute-Force Protection: 5 failed auth attempts trigger an instant 10-minute firewall block across all endpoints.
  • 🎵 Pure Rust MPEG-1 Layer 3 Audio Engine: Pure-Rust frame parser validates audio stream integrity and extracts playback duration, bitrate, and sample rate with zero C dependencies.
  • ⏯️ Resumable HTTP Range Streaming: Full 206 Partial Content support for seamless streaming into VLC, media players, or resuming interrupted network transfers.
  • 💾 Hardened SQLite WAL Storage: SQLite backend configured with Write-Ahead Logging (WAL), synchronous=NORMAL, and 30-second busy timeout for high-concurrency read/write safety.
  • 🕵️ Cloaked Embedded Dashboard: Zero-dependency dark management interface at /web with IP whitelist cloaking (returns 404 Not Found to unauthorized external scanners).

🚀 Quick Start

Option A: Pull Multi-Arch Image from GHCR (Recommended)

Run the pre-built multi-architecture container (amd64 and arm64 supported automatically):

docker run -d \
  --name league-voice-recorder-backend \
  -p 8443:8443 \
  -v $(pwd)/data:/app/data \
  -v $(pwd)/certs:/app/certs \
  -e ADMIN_KEY="your-super-secret-admin-key" \
  -e UPLOAD_KEY="your-upload-api-key" \
  -e PULL_KEY="your-pull-api-key" \
  --restart unless-stopped \
  ghcr.io/betterix/league-voice-recorder-backend:latest

Option B: Deploy with Docker Compose

  1. Clone the repository: bash git clone https://github.com/betterix/league-voice-recorder-backend.git cd league-voice-recorder-backend

  2. Configure your environment: bash cp .env.example .env # Edit .env with your strong API keys and credentials

  3. Start the service: bash docker compose up -d

  4. Verify health: bash curl -k -H "X-API-Key: YOUR_PULL_KEY" https://localhost:8443/api/v1/health

Core Architecture ARCHITECTURE.md

System Architecture

The League Voice Recorder Backend is a high-performance, asynchronous audio storage and sync service written in Rust using the Axum web framework and the Tokio asynchronous runtime.

1. High-Level Design Principles

1.1 Direct Internet Exposure (Native TLS 1.3)

Unlike legacy architectures that mandate an external Nginx, Apache, or Caddy reverse proxy, the service terminates TLS 1.3 directly on port 8443 using OpenSSL AEAD cipher suites (TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256).

Direct-port ingress provides significant operational advantages: - Zero Proxy Buffering: Standard reverse proxies buffer incoming requests into temporary disk files before forwarding to backend apps. This causes fatal upload dropouts and 504 Gateway Timeouts for large audio transfers (up to 250 MB). - Sub-Millisecond Handshakes: Axum-server negotiates TLS handshakes natively with zero proxy hops, delivering sub-millisecond response latencies. - Simplified Operations: Eliminates separate web server configuration files, proxy header passing bugs, and multi-container ingress orchestration.

1.2 Thread-Safe Lock-Free Concurrency

Rate limiting, connection tracking, active ban state, and IP intelligence caches are maintained in memory via lock-free concurrent hash tables (DashMap). Mutex contention is completely avoided across Tokio worker threads: - DashMap Sharded Locking: Read operations execute concurrently without blocking other reader or writer threads. - Sliding-Window Token Buckets: Failed authentication attempts and rate-limit windows are tracked in microsecond timestamps. - Zero Memory Allocation Overhead: State objects are allocated once at server startup and shared across all request handlers via Arc<AppState>.

1.3 Hardened SQLite WAL Storage

The database engine runs SQLite via sqlx::SqlitePool with optimized concurrency pragmas: - PRAGMA journal_mode = WAL;: Write-Ahead Logging allows concurrent readers to query the database while a writer is appending new recording metadata. - PRAGMA synchronous = NORMAL;: Reduces disk sync operations without sacrificing database integrity in WAL mode. - PRAGMA busy_timeout = 30000;: 30-second busy timeout eliminates "database is locked" errors under heavy concurrent scrimmage uploads. - PRAGMA foreign_keys = ON;: Enforces relational integrity across tables.

1.4 Real-Time Structured Access Logging & Noise Suppression

Every incoming request is processed by a custom Tokio middleware layer in src/lib.rs: - Real-Time Request Telemetry: Logs client IP, HTTP method, path, HTTP response status code, and latency in microseconds (µs) or milliseconds (ms). - Healthcheck Noise Suppression: Container monitoring agents probe /api/v1/health every 15–30 seconds. To prevent Docker logs from being spammed with thousands of redundant lines, successful health checks (200 OK) are automatically filtered out from console logs. If a health probe ever returns an error, it is instantly logged at warning/error level.

1.5 Bounded Memory Footprint (1.35 MiB Resident RAM)

By avoiding garbage-collected runtimes and using zero-copy byte streaming, the entire application consumes under 1.35 MiB of resident RAM in production. Memory usage remains completely flat regardless of whether the server is idling or streaming multiple concurrent 100 MB recordings.

Security & Protection SECURITY_AND_BOT_SHIELD.md

Security Model & Bot Shield

The backend implements a multi-layered defense architecture specifically designed for services directly exposed to the public internet.

1. Strict Three-Key Authentication

All API operations under /api/v1 require the X-API-Key HTTP header:

Key Role Target Audience Permissions
UPLOAD_KEY Scrim recording clients / players Upload scrimmage audio (POST), query recordings (GET), stream/download audio (GET), health check (GET). Destructive deletion attempts return 403 Forbidden.
PULL_KEY Coaches, analysts, synchronizers Query recordings (GET), stream/download audio (GET), health check (GET). Write and delete attempts return 403 Forbidden.
ADMIN_KEY Master administrative operator Unrestricted read, write, upload, delete (DELETE), and diagnostic access.

Constant-Time Verification

All key and credential evaluations use constant-time byte comparisons (subtle::ConstantTimeEq) to eliminate side-channel timing attacks.

2. Sliding-Window Rate Limiting

The in-memory rate limiter tracks requests per IP using sliding-window timestamps stored in thread-safe concurrent maps:

  • General API Limit: 120 requests per IP per minute (configurable via RATE_LIMIT_PER_MINUTE).
  • Upload Endpoint Limit: 10 uploads per IP per minute (configurable via UPLOAD_RATE_LIMIT_PER_MINUTE).
  • When a limit is reached, the server responds with 429 Too Many Requests along with a Retry-After: <seconds> HTTP header.

3. Brute-Force Authentication Defense

  • Failed authentication attempts (invalid or missing X-API-Key, or invalid web dashboard credentials) are tracked per client IP.
  • Upon reaching 5 failed attempts within 60 seconds (configurable via AUTH_FAILURE_LIMIT_PER_MINUTE), the IP is temporarily blocked across all endpoints for 10 minutes (429 Too Many Requests).

4. Zero-Tolerance Scanner & Exploit Probe Detection

Automated vulnerability scanners (e.g., Nikto, Censys, Shodan, automated WebDAV/PHP bots) are blocked before reaching application logic:

  1. Signature Detection:
  2. Sensitive dot files (.env, .git, .aws, .ssh, .vscode)
  3. Directory traversal sequences (../, ..\, %2e%2e%2f)
  4. CMS reconnaissance (/wp-, /wordpress, xmlrpc.php, rest_route=)
  5. Server-side script extensions (.php, .asp, .aspx, .jsp, .cgi)
  6. Admin panels (/phpmyadmin, /pma, /adminer, /cpanel)
  7. Spring Boot Actuators, consoles, metrics (/actuator, /console, /metrics, /telescope)
  8. GraphQL and MCP probe signatures (/graphql, /mcp, /v1/models, /sse)

  9. Suspicious HTTP methods (PROPFIND, SEARCH, MKCOL, CONNECT, etc.)

  10. Instant Permanent Ban:

  11. Any client IP matching scanner signatures is immediately banned permanently in the SQLite banned_ips table and rejected with 403 Forbidden.

  12. The ban persists across server restarts.

  13. Heuristic Client Error Tracker:

  14. Unauthenticated requests generating client errors (400 Bad Request, 404 Not Found, or 405 Method Not Allowed) are tracked.
  15. If an IP accumulates 5 client errors within 60 seconds, it is automatically banned for 60 minutes.

5. Hybrid Datacenter / VPS Bot Shield

Most malicious scanning originates from cloud hosting providers, virtual private servers (VPS), and automated crawler networks rather than residential player connections.

The backend employs a two-tier hybrid classifier:

  1. Fast Offline Keyword Filter: Evaluates Autonomous System (AS), Organization, and ISP strings against known cloud and hosting providers (digitalocean, amazon, hetzner, ovh, linode, vultr, choopa, datacamp, censys, shodan, leaseweb, scaleway, alibaba, tencent, oracle, etc.).

  2. Asynchronous External Intelligence: For uncached public IPs, queries ip-api.com asynchronously (1.8-second timeout). If the hosting or proxy flag is true, or known provider keywords match, the IP is classified as Datacenter/VPS.

  3. Persistent Classification Cache: Classifications are stored in memory (DashMap) and persisted to the SQLite ip_intel table.

  4. Bypass Policy: Requests carrying a valid X-API-Key or originating from configured WEB_ALLOWED_IPS management hosts or local/private networks (127.0.0.1, RFC1918) are completely exempt from datacenter blocking.

Audio Pipeline & Storage Mechanics

The audio subsystem is built for streaming high-capacity audio uploads and resumable partial downloads while maintaining bounded memory consumption.

1.1 Game ID Sanitization & Path Traversal Defense

  • Regex Boundary: Every game ID parameter is validated strictly against ^[a-zA-Z0-9_-]{1,64}$.
  • Injection Prevention: Any input containing path traversal sequences (../, ..\), directory separators (/, \), or null bytes (\0) is immediately rejected with 400 Bad Request.
  • Reserved Names: Protects against OS-reserved filenames (such as CON, PRN, AUX, NUL on Windows clients).

1.2 Bounded Memory Streaming (64 KB Chunks)

  • Zero Full-File Buffering: The server never buffers complete audio recordings in memory (tokio::fs::read is strictly prohibited).
  • Stream Flow: Uploads stream chunk-by-chunk using a fixed 64 KB buffer (CHUNK_SIZE = 64 * 1024) directly from the incoming HTTP multipart/binary stream to an isolated temporary file on disk (.tmp_<game_id>_<uuid>.mp3).
  • Real-Time Cryptographic Hashing: An incremental SHA-256 digest (ring::digest::Context) processes each 64 KB chunk in-flight as it passes through memory, computing the exact checksum with zero secondary disk reads.
  • Upload Size Guard: If the incoming byte stream exceeds MAX_UPLOAD_MB (default 250 MB), the upload is terminated immediately and returns 413 Payload Too Large, unlinking the partial temporary file.

1.3 Checksum Verification & Timing-Attack Prevention

  • Clients may supply an expected SHA-256 hash via the X-Checksum-SHA256 HTTP header.
  • The computed in-flight hash is compared against the client's provided checksum using constant-time equality (subtle::ConstantTimeEq).
  • If a hash mismatch occurs (e.g. corrupted network transfer), the temporary file is unlinked and the request returns 400 Bad Request.

1.4 Pure Rust MPEG-1 Layer 3 Frame Parsing

The audio engine validates audio stream validity using a pure-Rust MPEG frame parser without invoking external C libraries (such as FFmpeg, libmp3lame, or SoX): - ID3v2 Header Bypass: Automatically detects and safely skips ID3v2 metadata tags by decoding the 4-byte sync-safe integer length. - Frame Sync Word: Scans for the MPEG-1 Layer III 11-bit sync word (0x7FF / 0xFFE0). - Header Bitfields: Extracts MPEG audio version, layer index, bitrate index, sampling frequency, and padding bit. - Frame Length Calculation: text FrameSize = ((144 * Bitrate_bps) / SampleRate_Hz) + Padding - Playback Duration Calculation: text Duration_Seconds = (Total_Valid_Frames * 1152) / SampleRate_Hz - Integrity Validation: Rejects non-audio payloads, corrupted streams, or disguised executables with 400 Bad Request.

1.5 Atomic Two-Phase Commit & Rollback

  • Audio files are initially staged with unique temporary filenames (.tmp_<game_id>_<uuid>.mp3).
  • Once validation succeeds, the file is atomically renamed to <game_id>.mp3 using filesystem-level atomic rename (POSIX rename()).
  • If SQLite metadata insertion fails, a database rollback is executed and the audio file is cleanly deleted from disk.

2. Resumable Downloads & HTTP Range Requests

Clients, VLC players, desktop synchronizers, and browsers query: GET /api/v1/recordings/{game_id}/download

2.1 RFC 7233 Range Header Specifications

The storage layer parses HTTP Range headers for seamless audio scrubbing and resumed downloads: - Explicit Range: Range: bytes=0-1048575 (requests the first 1 MB chunk). - Open-Ended Range: Range: bytes=1048576- (requests from 1 MB through EOF). - Suffix Range: Range: bytes=-524288 (requests the final 512 KB of the file).

2.2 Response Specifications

  • Valid Range: Returns 206 Partial Content with Content-Range: bytes <start>-<end>/<total> and Content-Length.
  • Invalid / Out-of-bounds Range: Returns 416 Range Not Satisfiable with Content-Range: bytes */<total>.
  • Standard Request (No Range): Returns 200 OK with Accept-Ranges: bytes and Content-Disposition: attachment; filename="<game_id>.mp3".

  2. Only client IPs matching WEB_ALLOWED_IPS (comma-separated IP addresses or subnets) can access the interface.

Deployment & Operations

This document covers deployment options for the Rust backend: Docker Compose, native binary execution, and TLS certificates.

Prerequisites

Step-by-Step Setup

  1. Clone the repository and navigate to the directory: bash git clone https://github.com/betterix/league-voice-recorder-backend.git cd league-voice-recorder-backend

  2. Copy the environment template: bash cp .env.example .env

  3. Configure your production credentials in .env:

  4. Set strong random 32+ character secrets for UPLOAD_KEY, PULL_KEY, and ADMIN_KEY.
  5. Set WEB_USERNAME and a strong 16+ character WEB_PASSWORD.

  6. Set WEB_ALLOWED_IPS to your management IP address (or 0.0.0.0 if your IP changes frequently).

  7. Build and start the container: bash docker compose up -d --build

  8. Verify health: bash docker compose ps curl -k -H "X-API-Key: YOUR_UPLOAD_KEY" https://localhost:8443/api/v1/health

2. TLS Certificate Management

The backend listens natively over TLS 1.3 on port 8443.

2.1 Production: Let's Encrypt / CA Certificates

Place your certificate and private key in ./certs: - ./certs/cert.pem: Full certificate chain (PEM format). - ./certs/key.pem: Private key (PEM format).

Verify file permissions:

chmod 600 certs/key.pem
chmod 644 certs/cert.pem

2.2 Development: Automatic Self-Signed Certificates

When running with ENVIRONMENT=development or DEV_SELF_SIGNED_CERT=true, the backend automatically generates a self-signed ECDSA certificate with Subject Alternative Names (SANs) for localhost, 127.0.0.1, and your configured DOMAIN_NAME if missing from ./certs.

# Build release binary
cargo build --release

./target/release/league-voice-recorder-backend

cargo test

Security Policy

The League Voice Recorder Backend team takes the security and integrity of scrimmage audio and remote team data seriously. This document outlines our supported versions, threat model guidelines, and responsible vulnerability disclosure process.

🛡️ Supported Versions

[!IMPORTANT] Version 1.3.x is the latest and officially supported release stream. We strongly recommend all operators, teams, and developers run v1.3.x.

All legacy versions (including the 1.2.x Python implementation and earlier) are deprecated, incompatible, inefficient, and can be unsafe. Legacy versions will receive no further security patches, performance fixes, or maintenance.

Version Stream Release Architecture Supported Status
1.3.x Rust (Axum 0.8 + Tokio) ✅ Yes Active & Recommended (Hardened TLS 1.3, constant-time auth, bot shield)
1.2.x Python (FastAPI / Uvicorn) ❌ No End-of-Life (Incompatible, inefficient, non-hardened)
< 1.2.0 Legacy Scripts / Prototypes ❌ No End-of-Life (Unsupported)

⚠️ Why 1.3.x is Required

The v1.3.x series represents a complete re-architecture from the ground up in memory-safe Rust:

  1. Memory Safety & Bounded Resource Consumption: Operates under 1.35 MiB of RAM in production. Audio streaming is strictly bounded in 64 KB chunks, mitigating denial-of-service (DoS) via memory exhaustion.
  2. Timing Attack Elimination: All API credentials (UPLOAD_KEY, PULL_KEY, ADMIN_KEY) and web dashboard passwords are authenticated using subtle::ConstantTimeEq.
  3. Active Exploit & Scanner Defense: Includes automated zero-tolerance bans for vulnerability scanner probes (/.env, /.git, /actuator, PROPFIND), sliding-window brute-force rate limiters, and hybrid datacenter/VPS bot filtering.
  4. Direct-Port TLS 1.3: Direct native TLS termination eliminates the need for intermediate reverse proxy buffering, preventing truncation of large audio files.
  5. Schema Compatibility: The database schema and audio integrity hashing in 1.3.x are not compatible with the outdated 1.2.x architecture.

📋 Contribution Rules & Engineering Standards

All pull requests and code modifications must uphold the following architectural constraints:

1. Bounded Memory Streaming

  • Never read entire audio recordings into memory at once (e.g., avoid unbounded tokio::fs::read).
  • Always stream audio files in chunks (CHUNK_SIZE = 64 * 1024 / 64 KB) across uploads and downloads.
  • Honor HTTP Range headers (206 Partial Content) for resumable downloads.

2. Constant-Time Authentication

  • Any token, password, or API key comparison must use constant-time algorithms (subtle::ConstantTimeEq) to prevent timing side-channel attacks.

3. Noise-Free Access Logging

  • Real-time access logging is enabled for all API requests (reporting client IP, HTTP method, path, status, and duration).
  • Healthcheck requests (/api/v1/health) that return success must remain suppressed in stdout logs to eliminate Docker monitoring noise.

4. Atomic Storage & Database Consistency

  • If a database transaction or metadata insert fails during an audio upload, the staged audio file on disk must be unlinked/deleted immediately in a rollback handler.

5. Zero External Web Dependencies

  • The embedded web dashboard (/web) must remain completely zero-dependency without external CDNs, Google Fonts, or external tracking scripts.

6. Secrets & PII Discipline

  • Never commit real API keys, passwords, private keys, or actual user IP addresses.
  • Use RFC 5737 documentation IP prefixes (203.0.113.x or 198.51.100.x) in documentation, tests, and mock fixtures.
